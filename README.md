# Reply911 Emergency Incidents API

## Overview

A RESTful backend for registering Reply911 emergency incidents. Each incident includes an external incident code, response unit identifier, response window, dispatch cost, status and optional description.

## Architecture Overview

The application follows the layered structure of the Learning Center Platform reference. The **Emergency** bounded context contains the business model; **Shared** contains common contracts, auditing and infrastructure.

- **Domain:** aggregates, value objects, commands and repository contracts.
- **Application:** creation use cases, result handling and context facades.
- **Infrastructure:** Entity Framework Core mappings, MySQL repositories and persistence components.
- **Interfaces:** REST controllers, input/output resources and assemblers.

## Key Features

- Rejects duplicate incident codes.
- Requires the SLA deadline to be strictly later than the report timestamp.
- Provides SLA breach checks using DateTime values.
- Accepts zero or positive monetary values and requires a nonblank currency.
- Supports monetary multiplication and priority surcharge calculations that return a new amount.
- Defaults the incident status to Pending; also supports Reported, Attended and Cancelled.
- Database-generated integer primary key.
- Automatic creation and update timestamps.
- Structured HTTP error responses and interactive Scalar documentation.

The current implementation provides English messages only. English/Spanish localization required by the statement remains pending.

## Getting Started

### Prerequisites

- .NET 10 SDK
- A running MySQL server
- The dotnet-ef tool compatible with EF Core 10

### Setup Instructions

1. Open `Practica04.sln` or navigate to the project directory:

```powershell
cd .\Practica04
```

2. Set your MySQL credentials in `appsettings.Development.json`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "server=localhost;port=3306;user=root;password=YOUR_PASSWORD;database=Reply911_emergency"
  }
}
```

3. Restore, build and apply the existing migrations:

```powershell
dotnet restore
dotnet build
dotnet ef database update --context AppDbContext
```

If this checkout has no migrations yet, generate the initial migration before updating the database:

```powershell
dotnet ef migrations add InitialCreate --context AppDbContext
```

4. Run the development HTTP profile:

```powershell
dotnet run --launch-profile http
```

5. Open [Scalar](http://localhost:5099/scalar/v1) or the [OpenAPI document](http://localhost:5099/openapi/v1.json).

## API Endpoint

```http
POST /api/v1/emergency-incidents
```

Creates a `EmergencyIncident`. The identifier is generated by the database and is not required in the request.

The response contains id, guidCode, responseUnitId, reportedAtDate, slaDeadLineDate, dispatchCostValue and dispatchCostCurrency.

- **201 Created:** the record was saved successfully.
- **400 Bad Request:** request validation failed.
- **409 Conflict:** a uniqueness rule was violated.
- **500 Internal Server Error:** an unexpected server error occurred.

See `Practica04/Practica04.http` from the solution root for a sample request. No GET, update or delete operation is implemented.
